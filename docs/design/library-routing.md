# 媒体库路由：库自述收藏范围——设计

> 状态：v1 已实施（2026-07-27，R1–R4 全部完成，实施与设计一致；
> 实施期修正见各期注记）。
> 关联文档：[library.md](library.md)（媒体库架构，本文是其"选库"环节的扩展）、
> [metadata.md](metadata.md)（刮削档案——路由的事实来源）。

## 0. 定位与第一性

**问题**：多库用户（电影库 + 华语电影库 + 动漫库…）目前只有两种选库方式——
每次手选，或每 kind 一个默认库。订阅、手动下载、监听导入都无法按作品特征
（区域/类型）自动分流，"动漫进动漫库"要靠用户每次记得选。

**方案**（用户决策 2026-07-27）：**库自述收藏范围**。路由规则不是独立实体，
而是挂在库上的"本库收什么"声明；选库 = 在同 kind 的库里找收藏范围命中的那个，
都不命中落该 kind 的默认库。选型对比与否决理由：

- **独立路由规则表**（MoviePilot 目录规则形态）：表达力过剩、多一个要学的概念、
  规则与库两处配置易失同步——按区域/类型分库的真实场景用不到，否决；
- **库内二级分类目录**：解决的是"路径"不是"选库"，与本方案不互斥，留 v2；
- **粒度定位**：粗粒度（区域/类型）分库；细粒度聚合（"诺兰的电影"/"漫威宇宙"）
  定位为 v2 的库内二级目录与 v3 的播放器合集，**不引导用户为其分库**——
  分库意味着内容从主库消失（Emby 独立入口），多数用户的真实诉求只是磁盘归拢。

三条产品铁律（贯穿全部消费点）：

1. **规则只决定默认值**：订阅/下载弹窗预选路由结论，用户永远可以手动改库；
2. **路由永不失败**：任何异常（元数据不可得、无命中）都落该 kind 默认库，
   绝不阻断投递/入库——默认库就是"其他"的承接者；
3. **全程可解释**：预检、订阅时间线、入库结论都用中文写明"为什么进这个库"。

**粘性（作品级定格）**：作品一旦确定归属库，后续季/集/新版本跟随既有归属，
规则变更只影响新作品——否则改一次规则，一部剧的两季裂在两个库，Emby 里
直接变成两个条目。订阅场景借"创建时定格 `subscription.library_id`"零成本实现
（见 2.1）；监听导入的认领路径继承订阅定格（见 2.3）。

## 1. 路由模型

### 1.1 收藏范围声明：`library.match_rules`

库表新增一列，**存储从第一天就是通用条件结构**（承接 v2 的导演/公司/系列维度，
届时只加字段枚举与 UI 控件，零迁移零引擎改动）：

```json
// 动漫库（tv）：收"日韩的动画"
[
  {"field": "genres",          "op": "any_of", "values": [16]},
  {"field": "origin_countries","op": "any_of", "values": ["JP", "KR"]}
]
```

语义约定：

| 约定 | 内容 |
|---|---|
| 条件间 | **AND**（都满足才命中——"这个库收什么"的直觉语义，也让特异性排序自然成立） |
| 条件内 | v1 唯一算子 `any_of`：作品该字段与 `values` 有交集即满足 |
| v1 字段 | `genres`（TMDB genre **ID**）、`origin_countries`（ISO 3166-1 国家码） |
| 空列表 | 未声明收藏范围——不参与命中，只能被显式指定或作为默认库兜底 |
| 特异性 | = 条件条数。多库同时命中时条数多者赢；打平取 `id` 小者（创建早优先） |
| 未知字段 | 保守**不命中** + 日志告警（降级安全：新版本写的规则被旧代码读到时不误路由） |

**为什么 genres 存 ID 不存名字**：`tmdb_language` 是可配设置，
`media_metadata.genres` 存的是刮削语言的本地化名（`scrape_language` 字段为证）。
规则若存中文名，用户把语言切成 en 后所有规则**静默失效**——这类"配置还在、
悄悄不工作"的坑必须在模型层堵死。TMDB genre ID 全语言稳定（16=动画，
99=纪录…），内置一张 ID↔中文名映射表（movie 19 项 + tv 16 项，TMDB 多年未变）
负责 chips 展示与理由文案；国家码本身就是稳定码，无此问题。

**区域预设组**（纯前端概念，存储永远是国家码列表）：

| 预设 | 展开为 |
|---|---|
| 大陆 | CN |
| 港台 | HK, TW |
| 日韩 | JP, KR |
| 美国 | US |
| 欧洲 | GB, FR, DE, IT, ES, IE |
| 小语种 | IN, TH, RU |

（预设是捷径不是分区：新加坡/加拿大/澳大利亚/新西兰归不进任何组，
界面上逐个勾选。）

白名单模型表达不了"其他"——这不是缺陷：**收不进任何声明库的作品自然落
默认库，默认库就是"其他库"**。界面文案要把这层讲明（见第 4 节）。

### 1.2 作品画像：`RoutingFacts`

路由的输入是作品的三个事实：`kind`、`genre_ids`、`origin_countries`。
关键约束：**路由决策点不保证刮削档案已在库**——订阅创建只建 `media_item`
（最小身份闭包，无类型/地区），`MediaMetadata` 是异步刮削写入的。事实来源
按优先级取：

```
① media_metadata.genre_ids / origin_countries   —— 已刮削，断网可用
② TMDB 轻量详情（GET /{kind}/{tmdb_id}，不 append）—— 一次往返，genre id 原生返回
③ 都不可得 → facts = None → 路由回落默认库，理由写明"元数据暂不可得"
```

配套改动：`media_metadata` 新增 `genre_ids` 列（JSON），刮削时与 `genres`
同步写入（`MediaProfile` 提取处 TMDB 原始数据里 id 与 name 在同一数组，
顺手保留，成本为零）。老档案行 `genre_ids` 缺失时走 ②，元数据刷新任务
重刮后自愈。**提取口径与刮削共用同一代码路径**（`fetch_media_profile` 的
国家/类型提取抽成可复用小函数），防止两处口径漂移。

窗口极小的兜底 ③ 之所以可接受：识别/建档本身就依赖 TMDB（`ensure_media_item`、
`verify_resolve`），"身份确定了但 TMDB 恰好拉不到详情"只发生在②的单次请求
失败瞬间——落默认库 + 中文理由已是正确行为，不值得为它做重试队列。

### 1.3 路由算法

```
route(session, kind, facts) -> RouteDecision:
    候选 = 同 kind 且 match_rules 非空的库
    命中 = [lib for lib in 候选 if evaluate(lib.match_rules, facts)]
    if 命中: 取特异性最高，打平取 id 最小 → matched=True，reason="命中「动漫库」：类型=动画、区域=日韩"
    else:   默认库 get_default(kind)      → matched=False，reason="未命中任何收藏范围，落默认库「剧集库」"

evaluate(rules, facts) -> bool:
    facts 为 None → False
    all( set(facts[field]) & set(values) 非空  for 每条 rule )   # 未知 field 视为 False
```

纯函数、无 IO（facts 由调用方备好）、单测友好。`RouteDecision =
{library, matched, reason}`，reason 是直接可展示的中文句子——预检、活动、
入库结论三处共用，不各写各的文案。

## 2. 消费点

### 2.1 订阅：创建时定格（粘性的实现）

路由发生在**订阅创建那一刻**，结论固化进 `subscription.library_id`——
之后的每次投递读的都是定格值，`dispatch()` 的三级兜底逻辑**一行不改**：

- **弹窗预检**：`/subscriptions/download-routing-preview` 接受可选参数 `tmdb_id`。
  `library_id` 缺省且能取到 facts 时返回路由结论与理由，前端预选该库并展示
  "自动：命中「动漫库」（类型=动画）"，用户可改——改了就是显式指定，规则退让；
- **创建**：`payload.library_id` 为 None 时（前端异常/API 直调）后端兜底
  route 一次再定格；订阅时间线记一条活动："已按收藏范围入库到「动漫库」
  （命中：类型=动画）"；
- **`resolve_for_subscription` 的 NULL 分支**（老订阅/库被删后 SET NULL 的
  回落）：从 `get_default(kind)` 升级为 `route()`——语义不变（route 内含
  默认库兜底），老数据自动获得路由能力。

### 2.2 手动下载

下载弹窗与订阅弹窗同源：搜索结果**按作品分组**的条目带 tmdb 锚，预检同样
预选路由库；未分组的裸种子无锚无 facts，维持现状（默认库/手选），不猜。

### 2.3 监听导入：「自动路由」模式

`ImportWatch` 的目标从"必选某个库"变为二选一：

- **指定库**（现状，保留）：源目录内容固定进某库；
- **自动路由**：`library_id = NULL` + 新增 `kind` 列（auto 时必填）——
  识别出作品后走 `route()` 决定目标库。**kind 仍须先验**：识别链的语义
  按 movie/tv 分叉（条目名解析、季集分配），跨 kind 混合目录的判别是独立
  难题，本期不做（决策 5）。

`_ingest_entry` 的流程改造（目标库从入参变为识别后决策）：

```
识别身份 item
  ├─ info_hash 认领订阅身份 → 目标库 = 订阅定格的 library_id（resolve，
  │    含库已删的 route 兜底）——继承粘性与用户在订阅上的手选，不重新路由
  └─ 识别链身份（第三方下载）→ facts（1.2 三级来源）→ route() → 目标库
指定库规则：跳过以上决策，维持现状（规则声明压倒路由）
→ derive_save_path(目标库, …) → 探测/搬运/落账（不变）
```

**投递目录联动**（让"一个混合下载目录服务所有库"成立）：`resolve_dispatch_dir`
的查找顺序扩展为——目标库的专属规则 → 同 kind 的 auto 规则 → None。
订阅定格到动漫库、动漫库自己没配监听规则、但存在 tv 的 auto 规则时，
种子投进 auto 目录；完成后按 info_hash 认领回订阅身份、目标库=定格的动漫库，
闭环一致。

**校验变化**（`import_watch_config`，保存时前置报错原则不变）：

- auto + hardlink：源目录与**该 kind 全部路由可达的库**（声明库 + 默认库）的
  主根逐一同盘检测，列出不同盘的库名并讲明成因："源目录与「动漫库」（声明了
  收藏范围）的主根不在同一文件系统——自动路由可能选中这些库，硬链接会失败；
  请改用「复制」策略，或调整存储布局"。无声明且非默认的库（如跨盘的 strm
  归档库）路由永远不会选中，**不参与检测**——否则"跨盘归档库 + 硬链自动
  分流"的标准布局根本建不出规则（issue #79 的误伤）。已知漏网：订阅可手选
  任意同类型库定格、事后跨盘，由订阅链路体检（transfer_disk 按定格库检测）
  与搬运时的 EXDEV 中文报错兜底；
- 源目录与库根不重叠、全局唯一：不变；
- auto 规则每 kind 至多一条（两条 auto 规则监听不同目录没问题，但
  `resolve_dispatch_dir` 的投递落点会歧义——v1 直接限一条，简单明确）。

### 2.4 明确不做（本期边界）

- **存量不迁移**（用户决策 2026-07-27，研发阶段）：规则变更/新配置不触碰
  已入库文件；库扫描（原地入账）不参与路由——文件已经在某个库的根下，
  归属即事实；
- **库内二级分类目录**（导演/系列/公司粒度）：v2，有序规则列表 first-match
  形态，复用 1.3 求值器（选库用声明式、库内分组用列表式——各配各的问题）；
- **按 TMDB collection 自动建 Emby 合集**：v3 独立功能，不掺进路由。

## 3. 数据模型改动汇总

| 表 | 改动 | 说明 |
|---|---|---|
| `library` | + `match_rules` JSON，默认 `[]` | 1.1 的条件列表；空=未声明 |
| `media_metadata` | + `genre_ids` JSON，默认 `[]` | 刮削同步写；老行缺失走 TMDB 兜底，重刮自愈 |
| `import_watch` | `library_id` 改 nullable；+ `kind` str nullable | NULL=自动路由（此时 kind 必填）；指定库时 kind 冗余不填，由库推导 |

均为加列/放宽约束，SQLite 走 alembic batch 模式，可平滑升降。
`subscription` 无 schema 改动（`library_id` 已存在，语义从"手选值"扩展为
"手选或定格值"）。

## 4. 交互设计

- **库表单**新增"收藏范围"区（默认收起，空态文案："不声明收藏范围的库
  只作为兜底目标；该类型的默认库会自动承接所有未命中的作品"）：
  - 区域：预设组 chips（华语/日韩/欧美）多选，"更多"展开自选国家码；
  - 类型：按库 kind 展示对应 TMDB 类型 chips（中文名，存 ID）；
- **库列表卡片**：收藏范围摘要（"收：动画 · 日韩"）；同 kind 两库范围有交集
  且特异性相同时给只读警示（"「A」与「B」的收藏范围重叠且无法排序，
  命中时将优先创建更早的「A」"）——提示不阻断，用户加条件即可消解；
- **订阅/下载弹窗**：入库行显示"入库到：动漫库（自动：类型=动画）"，
  下拉可改；改后徽标消失（显式指定）；
- **监听导入表单**：目标下拉 = 各库 + "自动路由（电影）" + "自动路由（剧集）"。

## 5.1 订阅设定页与链路体检——✅ v1 已实施（2026-07-27）

背景（用户决策 2026-07-27）：下载器路径映射、监听导入、库根路径分散在三个
配置页，各自保存时都有前置校验，但正确性是**联合约束**——用户真正的问题
是"订阅后能不能自动下载并入库"。体检以这个问题为锚，落位在新的
「设置 → 订阅」分区（该分区同时是规则组等订阅级配置的家，此前缺位）。

- **链路体检**（`/subscriptions/automation-readiness`）：逐库预演
  投递（下载器就绪/投递目录/映射覆盖）→ 转移（硬链同盘/监听生效，watch
  模式）两段。判定复用真实投递/搬运的同一批原语（resolve_dispatch_rule
  兜底顺序、mapping_covers、st_dev 比对）——**口径同源**，不存在"体检说好、
  投递却挂"。三档结论：ok / warn（能转但降级，如 watchdog 缺失退化为兜底
  巡检）/ error（投递会被拒或不会自动入库）；每个红黄项带中文事实与修复
  跳转（下载器设置/监听导入/媒体库）；
- **提醒分层**：订阅弹窗预检管"这一单"（已有），订阅列表页警示横幅管
  "出问题了"（error 库数 >0 才出现，点击进设定页），订阅设定页管"全景
  与修复"——体检不靠用户主动逛设置页；
- **规则组**：设定页内只读清单（名称/默认标记/是否配置条件）；spec
  编辑器是独立设计议题，不做半成品；
- 体检只读、绝不成为第三个配置入口——修复动作全部跳转回原配置页。

体检 2.0（同日第二轮，用户诉求"更清晰的了解并作出配置"）：

- **流水线可视化**：检查项列表改为步骤条——公共段（资源搜索 → 下载器，
  所有库共享不逐库重复）+ 每库段（投递 → 转移(watch) → 入库），节点带
  状态色与真实路径，红黄项在卡片下方列事实与修复链接，「查看全部」展开
  绿项；新增全局**站点检查**（无可用站点=搜不到资源，error 级计入整体）；
- **开局清单**：三个必要件（站点/下载器/媒体库）任一缺失时，体检数据换
  一种读法——"下一步做什么"的 checklist（完成打勾、未完成给按钮），配齐
  自动让位给正常体检，同一页面从第一天用到第一百天；监听导入作为可选第
  四步只在脚注提及（不预设布局）；
- **修完自动重检**：页面重新获得焦点即重检（visibilitychange/focus），
  修复 → 回来 → 变绿的反馈闭环；映射红项文案带建议值（本机侧前缀已知，
  用户只补下载器视角一半）；
- **模拟一单**：搜一部片把「路由选库 → 投递落点 → 入库方式」完整预演
  （复用 dispatch-preview，零新后端逻辑），不真正订阅——用户主动验证
  自己对收藏范围与链路的理解的唯一工具。

## 6. 决策记录（2026-07-27）

1. 路由形态 = 库自述收藏范围（否决独立规则表：表达力过剩、双处配置失同步）；
2. 存储从第一天即通用条件结构，UI 只开区域/类型——v2 加维度零迁移；
3. 条件间 AND、条件内 any_of、特异性=条数、打平取 id 小；未知字段保守不命中；
4. genres 规则值存 TMDB ID（`tmdb_language` 可配，存本地化名会静默失效）；
5. auto 导入规则必须绑 kind（识别链需要 movie/tv 先验），每 kind 限一条；
6. 粘性 = 订阅创建时定格 `library_id` + 认领路径继承定格，不做入库时重路由；
7. 默认库即"其他"：白名单不表达否定，未命中一律落默认库，路由永不失败；
8. 存量不迁移、扫描不路由（研发阶段，且跨库迁移对播放器是删+增，代价大）。

## 7. 风险与开口

1. **genre 映射表维护**：TMDB genre 集合多年稳定，变更概率极低；真变了
   表现为"新类型 chips 里没有"，补一行常量即可，不影响既有规则；
2. **规则改后老订阅不动**：定格语义的直接推论，符合粘性预期；用户在订阅
   详情页手动改库即可（既有能力）；
3. **重叠警示只提示不阻断**：声明式模型没有全序，强校验会挡住合理配置
  （两个库故意共收一类、靠特异性分层）；提示 + 可解释预检兜底；
4. **v2 开口**：导演/公司/系列字段（typeahead 存 TMDB ID，开放集合不存名字）、
   库内二级目录规则（有序 first-match，复用求值器）、洗版与路由的交互
  （洗版替换应发生在作品既有归属库内——粘性已保证，届时验证即可）。
